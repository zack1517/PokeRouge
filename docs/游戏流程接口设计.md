## 1. 概述

### 1.1 模块定位

游戏流程模块负责 **一次 Run 从出发到结算的完整推进**，是连接「战斗 / 养成 / 经济」的主控逻辑。核心职责：

- **分段路线与行动点（AP）记账**：按「段（Segment）」推进路线，每段拥有固定上限的行动点，玩家在额度内自主选择节点；
- **节点生成与进入**：常驻节点固定出现、随机节点按概率出现、特殊事件节点带进度/次数限制；
- **战斗编排与结算**：为战斗节点构造敌人队伍并交给战斗模块，战斗结束后按节点类型执行奖励 / 惩罚 / 濒死 / 自回血结算；
- **经济系统**：金币的获得（路人、火箭队）与支出（商店、失败罚金）；
- **剧情线状态机**：神兽偶遇、火箭队剧情线、首领侵略事件的状态流转与「每 Run 一次」限制；
- **Run 结束判定**：胜利通关（普通 / 真结局）、失败结束、中途失败重试等。
- **抓捕记账**：登记每次成功捕获的物种与次数（驱动养成模块的「努力值成长」，见《README》特色机制）。

### 1.2 对外提供的服务

| 服务 | 说明 | 使用方 |
|------|------|--------|
| Run 生命周期 | 开局（携带初始队伍）、逐段推进、结局判定 | UI、主循环 |
| 路线/节点视图 | 当前段可选节点、AP 余额、段号 | UI（路线地图） |
| 节点结算 | 战斗结果 → 金币/道具/惩罚/治疗/推进 | UI、战斗模块联动 |
| 商店与经济 | 商品列表、购买、金币变动 | UI |
| 剧情线状态查询 | 神兽/火箭队/侵略事件可触发性 | UI、事件节点 |
| 抓捕记账 | 物种→捕获次数（供养成模块读取） | 养成模块 |
| 存档协同 | 提供 Run 快照编解码（建议并入存档系统） | 存档模块 |

### 1.3 设计约束

- 纯 JDK 17 实现，**不引入 JSON 等第三方序列化依赖**，不依赖任何 JavaFX 类型，可独立测试。
- 随机性全部经由注入的随机源（`RandomSource`）驱动，便于测试确定性与复现。
- 战斗细节（出手顺序、伤害、天气、异常）**不属于本模块**：本模块只负责构造敌方队伍、调用战斗桥、按结果结算。
- 数值（AP 上限、金币数额、商店规模、敌人等级曲线等）集中放 `FlowConfig`，标注 `[待配置]` 的项待组长评审后定值。
- 包位置：`com.bao01.flow`（实现文件：`FlowController.java`、`FlowConfig.java`、`BattleAdapter.java`、`FightResult.java`、`NodeType.java`、`Cat.java`、`RouteOption.java`、`NodePool.java`、`RunSummary.java`、`StoryFlags.java`、`CaptureLedger.java`、`ActionPoints.java`、`Ending.java`、`ShopOffer.java`、`RandomSource.java` 等）。
- 运行于 dev 的 `org.example.model.{Player,Pokemon,Item}` 与 `org.example.data.GameData` 之上，只依赖其公共 API，**不修改 org.example / dev**。

## 2. 数据模型（Model）

> 数据模型为 `com.bao01.flow` 下的顶层不可变 `record` / `enum`，每型一个文件（无 `FlowData` 容器类）；可变状态（段号/AP/金币/剧情线/账本）由 `FlowController` + `ActionPoints` 持有。

### 2.1 运行对象（不落盘 · dev 提供）

流程持有并操作 dev 的 `org.example.model.Player`（同一实例也传给战斗桥与存档模块）：

- `Player`：`getParty()`（只读）、`addToParty(Pokemon)`、`getBag()`、`healParty()`、`getActiveIndex()`/`setActive(int)`、`leadWithFirstHealthy()`。
- `Pokemon`：`getName()`、`getLevel()`、`getCurrentHp()`/`getMaxHp()`、`heal(int)`、`takeDamage(int)`、`isFainted()`。
- `GameData`：`allSpecies()` / `allItems()` / `createPokemon(id, level)` / `item(id)`（数据源：dev 资源目录 `data/*.csv`）。

### 2.2 NodeType（节点类型）

```java
/** 节点类别：决定结算方式。 */
public enum Cat { COMBAT, SERVICE, STORY, MILESTONE }

public enum NodeType {
    TRAINER    ("路人",          Cat.COMBAT),     // 常驻；胜得金币，败扣金币
    WILD       ("野外精灵",       Cat.COMBAT),     // 常驻；可捕获；败扣金币
    ROCKET     ("火箭队",         Cat.COMBAT),     // 随机；不可失败，败即结束 Run
    LEGEND     ("神兽偶遇",       Cat.COMBAT),     // 随机+进度限制；每 Run 一次；败扣金币
    HOSPITAL   ("医院",          Cat.SERVICE),    // 常驻；治疗濒死/受伤
    SHOP       ("商店",          Cat.SERVICE),    // 随机；购买道具/回复品/技能机（[待配置]）
    ROCKET_BOSS("火箭队抓捕神兽", Cat.STORY),      // 后期剧情事件；可自选进入；首领战不可失败
    GYM        ("道馆战",         Cat.MILESTONE),  // 必然节点；AP 耗尽触发；可失败一次
    ELITE_FOUR ("四天王连打",     Cat.MILESTONE),  // 路线终点前必然触发；可失败一次
    CHAMPION   ("Boss 冠军战",    Cat.MILESTONE),  // 路线终点必然触发；不可失败
    INVASION   ("首领侵略战",     Cat.MILESTONE);  // 条件必然触发（见 §6）；不可失败

    private final String label;
    private final Cat cat;
    public String label();   // 中文展示名
    public Cat cat();
}
```

> 说明：`NodeType` 只表达「种类」，**不表达行动点消耗**。AP 消耗与“随机为 0 / 必然 0”等修饰，由 `RouteOption` 在实例级表达（见 2.4），避免枚举内写死分支规则。

### 2.5 CaptureLedger（抓捕记账）

```java
public record CaptureLedger(Map<String, Integer> catchesBySpecies) {

    public static CaptureLedger empty();
    public CaptureLedger record(String species);  // 成功捕获后 +1（返回新副本）
```

### 2.6 RunSummary（对外只读快照 · 供 UI / 存档 / 养成）

```java
public record RunSummary(
        int segmentNo,          // 当前段号（从 1 开始）
        int apLeft,             // 剩余 AP
        int apCap,              // 本段 AP 上限
        int gold,               // 当前金币
        StoryFlags story,       // 剧情线状态
        CaptureLedger ledger,   // 抓捕计数
        List<RouteOption> options,  // 当前可选节点
        NodeType nextMilestone, // 下一个必然节点（GYM/ELITE_FOUR/CHAMPION/INVASION）；**派生值**：无则 null
        // ---- 以下为 v2（存档）新增：完整还原一次 Run 所需的其余状态 ----
        boolean inRoute,        // true=常规路线阶段，false=终局（终盘里程碑）阶段
        boolean gymRetried,     // 道馆已重试一次（第二次失败即 RUN_OVER）
        boolean eliteCleared,   // 四天王已通过
        boolean eliteRetried,   // 四天王已重试一次（不结束 Run）
        boolean championCleared,// 冠军已击败
        boolean invasionCleared,// 侵略战已通过
        Ending ending,          // 结局；null = 进行中
        List<ShopOffer> shopStock) {  // 当前商店货架（不在商店节点时为空表）

    public boolean inFinalPhase();   // 是否处于终局阶段
    public boolean isOver();         // ending != null
}
```

> **16 个字段**中，后 8 个是 v2 为「存档能精确还原 Run」而补齐的。`nextMilestone` 是**派生值**（由 `inRoute` / 各里程碑标记 / `canEnterAny()` 推出），不由存档直接还原，因此构造快照时必须让它与其余字段自洽。
> 快照**不含** `FlowController.pendingFight`（对局过程态）：读档后从该节点入口重来，见 §7。

### 2.7 Ending（结局）

```java
public enum Ending {
    RUN_OVER,      // Run 失败结束（含不可失败战斗战败、道馆/四天王二败）
    NORMAL_CLEAR,  // 普通通关（未开火箭队线：击败冠军即通关）
    TRUE_CLEAR     // 真结局（开线且未提前击败首领：冠军后再过首领侵略战）
}
```

### 3.2 RandomSource（随机源 · 可注入测试）

```java
public interface RandomSource {
    int nextInt(int bound);
    double nextDouble();
    boolean chance(double p);       // p≤0 恒 false，p≥1 恒 true
    static RandomSource system();   // ThreadLocalRandom 实现（生产）
    static RandomSource seeded(long seed);  // 固定种子实现（回放/调试/冒烟测试）
}
```

> **固定随机种子**：`seeded(seed)` 内部为 `new java.util.Random(seed)`，与 `system()` 语义完全一致，
> 仅随机序列可复现——同一 seed 必然重放出同一条路线（节点池、AP 消耗、商店、敌人选择等全部一致）。
> 用途：bug 复现（把 seed 写进问题单）、无头冒烟测试、录像回放。

### 3.3 BattleAdapter（战斗桥 · 由 feature/battle 对接实现）

> 职责边界：流程模块不直接操作战斗内部状态，只通过本桥**开局一场战斗**；对局推进与输赢判定由 feature/battle 实现。流程与战斗之间**不含**进行中对局查询接口——一场对局结束后由 UI/接线方调用 `FlowController.settleFight(NodeType, FightResult)` 回填结果。

```java
public interface BattleAdapter {

    /**
     * 开局一场流程战斗。
     *
     * @param player   我方玩家（流程持有的同一实例，战斗中对 HP/背包的修改直接反映到流程）
     * @param foes     敌方精灵列表（流程按节点构造，见 3.4 buildFoeTeam）
     * @param canFlee  是否允许逃跑（WILD / LEGEND 可逃；其余节点逃跑视为败北）
     * @return 开局日志（供 UI 展示；对局后续驱动由 UI / 战斗模块接管）
     */
    List<String> startBattle(Player player, List<Pokemon> foes, boolean canFlee);
}
```

> 注：敌方 `List<Pokemon>` 的构造（按段等级、按节点类型选物种）由流程模块负责，见 3.4 `buildFoeTeam`。流程侧用 `com.bao01.flow.FightResult`（见 3.4 末）表达对局结局，与 `BattleAdapter` 的返回解耦。

### 3.4 FlowController（流程门面）

> 采用**实例有状态**控制器，由主循环/UI 持有；我方队伍是传入的 `org.example.model.Player` 实例（`startRun`/`restored` 形参），方法返回 `List<String>` 叙事日志，便于 UI 直接展示。

```java
public final class FlowController {

    /** 开局：携带初始 Player 进入第 1 段，重置 AP，生成本段可选节点池。 */
    public static FlowController startRun(Player starter, RandomSource rnd, BattleAdapter battle);

    /** 开局（兼容带 cfg 形参的调用；数值均走静态 FlowConfig）。 */
    public static FlowController startRun(Player starter, FlowConfig cfg, RandomSource rnd, BattleAdapter battle);

    /** 开局（固定随机种子）：等价于 rnd = RandomSource.seeded(seed)。 */
    public static FlowController startRun(Player starter, long seed, BattleAdapter battle);

    /** 从 Run 快照恢复（已实现，见 §7；过程态战斗 `pendingFight` 不随快照保存）。 */
    public static FlowController restored(Player player, RunSummary snapshot, BattleAdapter battle);

    /** 从 Run 快照恢复（固定随机种子：续玩部分同样可复现）。 */
    public static FlowController restored(Player player, RunSummary snapshot, long seed, BattleAdapter battle);

    // ============ 状态查询 ============
    public RunSummary summary();          // 完整 16 字段快照（段号/AP/金币/剧情/账本/选项/里程碑标记/结局/商店）
    public int gold();
    public int apLeft();
    public int segmentNo();
    public StoryFlags story();
    public CaptureLedger ledger();
    public boolean isOver();
    public Ending ending();               // null = 进行中
    public NodeType nextMilestone();      // 常规段→GYM；终局依次 四天王/冠军/侵略；结束→null

    // ============ 节点选择 ============
    public List<RouteOption> options();   // 本段当前可选节点（按序可进入）

    /** 进入可选节点（下标对应 options()）：扣 AP → 执行该节点逻辑。 */
    public List<String> enter(int optionIndex);

    /** 触发当前必然节点（nextMilestone 非空时）：道馆/四天王/冠军/侵略 的开局。 */
    public List<String> startMilestone();

    // ============ 节点逻辑 ============
    public List<String> visitHospital();          // 医院：治疗全员（收费 hospitalCost，默认 0）
    public List<ShopOffer> shopStock();           // 商店：本段商品（随段号变多）
    public List<String> buy(int shopIndex);       // 购买；金币不足返回提示日志

    /** 构造某 COMBAT 节点的敌方精灵（等级 = FlowConfig.enemyLevel(segmentNo) 附近）。 */
    public List<Pokemon> buildFoeTeam(NodeType type);

    // ============ 战斗结算 ============
    /** 战斗结束后由 UI 调用：按节点类型执行奖惩、濒死处理、自回血、剧情线推进、必然节点触发。 */
    public List<String> settleFight(NodeType fought, FightResult outcome);

    /** 捕获尝试：对目标（战败的野生/神兽）执行一次捕获判定，成功记入抓捕账本。 */
    public List<String> attemptCatch(Pokemon target);

    // ============ 存档协同 ============
    /** Run 快照 → 单行调试摘要（`RUN|seg=..|ap=../..|gold=..|phase=ROUTE|FINAL|next=..|ending=..|options=N|caught=N`）。落盘不走本方法，走 `SaveManager` 的文本格式。 */
    public String toText();
}
```

## 4. 节点结算规则（流程主状态机）

> 由 `settleFight` / `enter` 统一驱动，规则出处：《README》「行动点机制 / 失败与惩罚规则 / 濒死恢复规则 / 节点自回血」。

### 4.1 AP 消耗（表）

| 节点 / 行为 | AP | 备注 |
|---|---|---|
| 野外精灵（偶遇） | 1 | 有概率消耗为 0（`wildZeroApChance`） |
| 路人 | 2 | |
| 医院 | 1 | |
| 商店 | 1 | 随机出现，规模随进度增长 |
| 神兽偶遇（正常触发） | 1 | 仅后期、每 Run 一次 |
| 神兽偶遇（火箭队线必然触发） | 0 | 大师球获得后必然出现、强制进入 |
| 火箭队节点 | 2 | 与路人一致 |
| 火箭队抓捕神兽事件 | 0 | 后期剧情选项（[待确认] 是否需 AP） |
| 道馆 / 四天王 / Boss / 侵略 | 0 | 必然触发 |

- 段开始时 AP 重置为该段上限（`segmentApCap(segmentNo)`）。
- **AP 耗尽** → 无可进入的可选节点 → 强制触发 `GYM` → 通过后进入下一段。
- 行动点不足以进入任何剩余节点且未耗尽？——视为不可再进，直接进入必然节点（实现细节：`enter` 拒绝 apCost > apLeft 的选项）。

### 4.2 战斗失败惩罚（表）

| 战斗类型 | 败后处理 | 是否中断 Run |
|---|---|---|
| 路人 / 野外精灵 / 神兽战 | 扣金币 `trainerFailPenalty` | 否，可继续 |
| 火箭队战 / 抓捕事件首领战 / 首领侵略战 | **不可失败** | 是（`RUN_OVER`） |
| 道馆战 / 四天王连打 | 允许失败一次：扣大量金币；**再次失败**结束 Run | 仅二败时 |
| Boss 冠军战 | 不可失败 | 是（`RUN_OVER`） |

### 4.3 濒死与自回血

- 战斗结算时：我方濒死（HP=0）成员**不恢复**；只能靠医院或道具（复活药等）治疗。
- **每通过一个节点后**：队伍中未濒死成员自动恢复 `maxHp / 5`（整数除法向下取整，最小 1，向上取整到 1 便于观测 [待确认]）；濒死成员不享受。
- 医院节点：治疗全部成员（含濒死）至满血（是否收费 `hospitalCost`，默认 0）。

### 4.4 抓捕流程

```
战斗胜利（野外/神兽战，目标未被我方行动 KO 而是被捕获状态）
  → UI 调 attemptCatch(target)
    → 捕获判定（概率 [待配置]）
      → 成功：ledger.record(物种)；加入队伍/触发同类合并/性格选择（调用养成模块，接口见 §8）
      → 失败：目标逃跑或继续（规则 [待确认]，默认仅一次判定，失败即该个体不可再抓）
```

## 5. 一段路线的典型推进（伪代码）

```
startRun(starterPlayer, rnd, battle)
  loop:
    options = NodePool.roll(segmentNo, story, rnd)   // 常驻 + 随机商店/火箭队/神兽(受次数/进度限制)
    while 有可进入的可选节点:
      ui 选择 node
      enter(idx):
        apLeft -= apCost
        if COMBAT/STORY → buildFoeTeam(type) + battle.startBattle(player, foes, canFlee)  // 交由 feature/battle
        if HOSPITAL → visitHospital
        if SHOP → 展示 shopStock / buy
        # 对局结束（胜负/逃跑）后由 UI 调 settleFight(type, FightResult):
        #   奖惩 / 濒死处理 / 自回血（非必然节点） / 剧情线推进（§6）
        #   每次战斗结算后 refreshOptions() 重新抽一组可选节点
    if 本段无必然节点（GYM 已过/不在常规段） → segmentNo++，重置 AP，敌人等级抬升
```

## 6. 剧情线状态机（神兽 / 火箭队 / 侵略）

> 规则出处：《README》「特殊事件进阶规则：神兽与火箭队」「一次 Run 的典型节奏」。

### 6.1 触发条件汇总

| 节点/事件 | 出现条件 |
|---|---|
| 神兽偶遇 | 仅后期段；`!legendaryEncountered`（每 Run 一次） |
| 火箭队节点 | 各时期随机 |
| 「火箭队抓捕神兽」剧情事件 | `rocketEntered` 且后期段可选；可自选进入 |
| 抓捕事件首领战 | 进入上述事件后触发；**不可失败**；胜 → `masterBallHeld=true`、`rocketBossDefeated=true` |
| 神兽偶遇（必然） | `masterBallHeld` 时强制出现一次（`forced=true`，AP=0） |
| 四天王连打 | Boss 战前必然（可失败一次） |
| Boss 冠军战 | 路线终点必然（不可失败） |
| 首领侵略战 | `championDefeated && rocketEntered && !rocketBossDefeated`（**不可失败**） |

### 6.2 结局判定

```text
击败冠军后：
  若 rocketEntered == false        → NORMAL_CLEAR（无抓捕/侵略事件）
  若 rocketEntered && bossDefeated → NORMAL_CLEAR（首领已提前击败，无侵略）
  若 rocketEntered && !bossDefeated→ 触发 INVASION
      击败侵略首领 → TRUE_CLEAR
      战败         → RUN_OVER
```

## 7. 存档协同（**已实现** · v2）

- 落地版本：《存档接口设计.md》**v1.3**，`SaveData.FORMAT_VERSION = 2`。
- `SaveData.World` 已追加可选字段 `RunSummary run`（保留 `World(version, player)` 重载 + `hasRun()`）；`PlayerData` 追加 `String name`（训练家名）。
- 存档文本新增段：`RUN`（段号 / 剩余AP / 金币 / 阶段 / 必然节点 / 结局）、`STORY`（6 位剧情线）、`FLAGS`（5 位里程碑）、`CAUGHT` + `CATCH`（抓捕账本）、`OPTIONS` + `OPTION`（当前可选节点）、`SHOP` + `OFFER`（商店货架），外加可选 `NAME` 行。标记明细见《存档接口设计.md》§5.1。
- 旧档兼容：v1 档（无 `NAME`/`RUN`）读出 `name = null`、`run = null`，队伍 / 出战位 / 背包照常重建；版本号高于 `FORMAT_VERSION` 仍拒绝加载。

恢复顺序（已在 `SaveManager` + `FlowController.restored(...)` 中实现）：

```
readFromFile(path) → World
  → SaveManager.restorePlayer(world)                 # 重建 Player（用存档里的训练家名）
  → world.hasRun() ? FlowController.restored(player, world.run(), adapter)
                   : 由主循环决定是否从段首新开 Run
```

`FlowController.restored(Player, RunSummary, BattleAdapter)` 内部走私有 `applySnapshot(RunSummary)`：

| 快照字段 | 还原方式 |
|---|---|
| `segmentNo` / `gold` / `options` / `story` / `ledger` 及各里程碑标记 | 直接赋值 |
| `apLeft` | `ActionPoints.restore(segmentNo, apLeft)`——`apCap` 由 `FlowConfig.segmentApCap(segmentNo)` **重算**，`apLeft` 截断到 `[AP_FLOOR, apCap]` |
| `ending` | 直接赋值（`null` = 进行中） |
| `shopStock` | 直接赋值，读档后仍可继续 `buy(index)` |
| `nextMilestone` | **不还原**：派生自 `inRoute` + 里程碑标记 |
| `pendingFight` | 置 `null`（读档后再次进入该节点即可重开） |

> **已修 Bug**：早期 `restored` 用 `ap.resetForSegment()` 恢复，会把 AP 刷成本段满值（读档回血）。现在按存档里的 `apLeft` 精确还原，`SaveDemo` 用例 7 有专门断言守着。

对局中断续档（战斗中存档）：战斗过程快照归属 feature/battle，本模块提供 `settleFight` 供恢复后继续结算；存档本身不落盘 `pendingFight`。

**随机源不落盘**：`RandomSource` 的内部状态未进存档，读档后的随机序列另起（`restored` 用 `RandomSource.system()`）。存档中的确定性字段不受影响。

## 9. 健壮性、扩展与验证

### 9.1 健壮性

| 场景 | 行为 |
|---|---|
| `enter` 选项 AP 不足 | 拒绝并返回提示，不扣 AP |
| AP=0 且仍有可选节点 | 不再允许进入，强制进入必然节点 |
| 金币为负（失败罚金超额） | 扣至 0，不产生负余额 |
| 商店金币不足 | 拒绝购买 |
| 神兽偶遇重复触发 | 受 `legendaryEncountered` 每 Run 一次限制，不重复 |
| 已击败抓捕首领后 | 不再触发侵略战（`rocketBossDefeated` 短路） |
| 段末敌人等级 | `enemyLevel(segmentNo)` 单调递增，越界按末段处理 |
| 存档快照不一致 | 校验失败返回异常并拒绝恢复 |

### 9.2 向后兼容扩展

- 数值全部集中 `FlowConfig`；新增节点 = `NodeType` + 结算分支 + AP 表，不动其它模块。
- `NodeType` 的语义只增不改；`RouteOption` 承载实例级修饰（0 AP、强制）。
- 预留给未来的扩展点：道具掉落表、技能机商店、天气对流程的影响、难度选项——新增配置项即可。
